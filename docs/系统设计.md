# AgentMusic 系统设计

## 1. 设计目标

AgentMusic 的目标不是再做一个“Spotify 网页壳”，而是做一个以**站内身份**和**站内数据**为核心的 AI 音乐产品：

- 用户不登录 Spotify，也能使用基础音乐 Agent 能力。
- 用户登录站内账号后，可以拥有“我的歌单 / 我的收藏 / 我的推荐历史 / 我的会话记忆”。
- 用户连接 Spotify 后，可以把 Spotify 当成一个增强型 Provider，而不是唯一生命线。

这条路线的关键变化是：

- **用户核心身份**从“Spotify 用户”改为“AgentMusic 用户”。
- **音乐数据能力**从“只接 Spotify”改为“Provider 可插拔”。
- **推荐与记忆**从“平台外部数据驱动”改为“站内行为数据 + 外部增强”双驱动。

## 2. 产品边界

### 2.1 必须实现

- 站内账号系统
- 游客模式
- 站内歌单与站内收藏
- 本地音频导入能力，MVP 至少支持非 DRM 的 `m4a` 文件
- 站内推荐历史与 Agent 会话
- Agent 驱动的推荐 / 查询 / 播放队列控制
- 可扩展的音乐 Provider 抽象层

### 2.2 可以增强但不能依赖

- Spotify 登录
- Spotify 用户歌单导入
- Spotify 收藏同步
- Spotify Top Tracks / Top Artists 画像增强
- Spotify 用户态播放控制

### 2.3 明确不做的假设

- 不假设每个用户都有 Spotify 账号
- 不假设用户愿意登录 Spotify
- 不假设 Spotify `preview_url` 足够支撑完整音乐体验
- 不假设未来只有 Spotify 一个外部数据源

## 3. 核心原则

### 3.1 站内身份优先

用户首先属于 AgentMusic，自身的歌单、收藏、偏好、历史推荐和会话记忆都应该挂在站内用户 ID 上，而不是挂在 Spotify 用户 ID 上。

### 3.2 外部 Provider 插件化

Spotify 是一个 Provider，而不是系统根节点。未来如果接入其他音乐源，只应新增适配器，不应推翻业务层。

### 3.3 推荐与记忆内生化

系统的个性化能力主要来源于站内行为数据：

- 搜索
- 收藏
- 建歌单
- 点赞 / 点踩
- 播放 / 跳过
- Agent 对话历史

Spotify 用户画像属于增强输入，而不是唯一输入。

### 3.4 音频能力单独建模

“能不能看到歌曲”与“能不能播放歌曲”不是同一件事。系统需要单独建模音频来源，避免把元数据能力和播放能力混成一层。

## 4. 总体架构

推荐采用“单仓前后端 + 后端 Agent 编排 + Provider 适配层”的结构。

### 4.1 架构分层

1. Presentation Layer  
   React 前端，负责页面展示、聊天交互、站内播放器、歌单管理和多模式 UI。

2. Application API Layer  
   Express 路由层，负责认证、鉴权、会话入口、接口组合和模式分流。

3. Domain Service Layer  
   负责站内账号、歌单、收藏、推荐、会话、行为记录、反馈、播放队列等业务逻辑。

4. Agent Orchestration Layer  
   负责任务理解、工具选择、推荐生成、回复组织、动作编排和记忆写回。

5. Provider Adapter Layer  
   封装 Spotify 等外部音乐源，统一为标准化的查询、推荐、导入、预览音频能力。

6. Storage Layer  
   保存站内用户、歌单、收藏、推荐历史、Agent 会话、行为事件、Provider 绑定关系。

## 5. 三种运行模式

### 5.1 游客模式

适用对象：不登录任何账号的访客。

能力：

- 浏览公开音乐目录
- 搜索公开音乐元数据
- 体验 Agent 通用推荐
- 听可用的预览音频

限制：

- 无法保存个人歌单和收藏
- 无法做真正个性化推荐
- 无法访问 Spotify `/me` 资源

### 5.2 站内账号模式

适用对象：登录 AgentMusic 账号的用户。

能力：

- 保存站内歌单和收藏
- 保存会话与推荐历史
- 基于站内行为生成个性化推荐
- 使用站内播放器和播放队列

限制：

- Spotify 用户态能力仍不可用

### 5.3 Spotify 增强模式

适用对象：站内账号已登录，且额外绑定 Spotify 账号的用户。

能力：

- 导入 Spotify 歌单
- 读取 Spotify 收藏和公开/用户画像数据
- 将 Spotify 历史偏好纳入推荐
- 解锁需要用户授权的 Spotify 功能

## 6. 核心模块

### 6.1 前端模块

- Auth UI  
  处理游客、站内登录、Spotify 绑定三种状态展示。

- Library UI  
  展示站内歌单、站内收藏、导入的本地音频，以及导入的外部内容。

- Player UI  
  处理当前播放队列、进度、播放控制和音源可用性提示。

- Agent UI  
  处理中间聊天工作台、上下文展示、推荐结果卡片、动作反馈。

- Recommendation History UI  
  展示历史推荐版本、反馈记录、再次播放入口。

### 6.2 后端模块

- Local Auth Service  
  站内账号注册、登录、会话、Token 管理。

- Provider Link Service  
  管理用户与 Spotify 等外部 Provider 的绑定关系。

- Catalog Service  
  抽象搜索、专辑、艺人、歌单、曲目详情等公开目录能力。

- Local Media Service  
  负责本地音频导入、元数据提取、资源管理和可播放性校验。

- Library Service  
  管理站内歌单、收藏、导入映射和同步状态。

- Recommendation Service  
  基于站内行为、Agent 约束和 Provider 数据生成推荐结果。

- Conversation Service  
  管理会话、消息、Agent 执行轨迹。

- Memory Service  
  保存长期偏好、近期行为、反馈标签和推荐记忆。

- Player Action Service  
  将 Agent 输出动作转成统一播放器指令。

## 7. Provider 抽象设计

Provider 层应统一暴露类似下面的能力：

```ts
type MusicProvider = {
  name: string
  search(query: string, options?: SearchOptions): Promise<SearchResult>
  getTrack(id: string): Promise<Track>
  getAlbum(id: string): Promise<Album>
  getArtist(id: string): Promise<Artist>
  getPlaylist(id: string): Promise<Playlist>
  getRecommendations(input: RecommendationInput): Promise<Track[]>
  getPreviewAudio(trackId: string): Promise<AudioPreview | null>
  importUserLibrary?(userLink: ProviderLink): Promise<ImportResult>
  importUserPlaylists?(userLink: ProviderLink): Promise<ImportResult>
  getUserProfile?(userLink: ProviderLink): Promise<ProviderUserProfile>
  controlRemotePlayback?(userLink: ProviderLink, action: PlaybackAction): Promise<void>
}
```

业务层永远只依赖这个接口，不直接依赖 Spotify 具体字段结构。

## 8. 数据模型

### 8.1 核心实体

- `users`  
  站内用户表，系统第一身份。

- `sessions`  
  站内登录会话。

- `provider_links`  
  用户与外部 Provider 的绑定关系，如 Spotify access token、refresh token、provider user id。

- `library_playlists`  
  站内歌单元信息。

- `library_playlist_items`  
  站内歌单歌曲列表。

- `library_favorites`  
  站内收藏关系。

- `audio_assets`  
  站内管理的本地音频资源，至少支持非 DRM 的 `m4a` 文件，后续可扩展 `mp3`、`wav`、`flac`。

- `playback_queues`  
  当前或历史播放队列。

- `listening_events`  
  播放、跳过、停留时长、重复播放等行为日志。

- `recommendation_runs`  
  一次推荐的元信息。

- `recommendation_items`  
  某次推荐的歌曲明细和排序。

- `conversations`  
  Agent 会话。

- `messages`  
  用户消息、Agent 回复、工具执行摘要。

- `feedback_events`  
  点赞、点踩、删除、重生推荐等反馈。

### 8.2 Provider 关联字段

站内数据与外部数据通过 `source_type + source_id` 关联，例如：

- `source_type = spotify`
- `source_id = spotify:track:xxx`

这样同一个站内歌单可以容纳不同 Provider 的歌曲，不需要硬绑定 Spotify。

## 9. 音频策略设计

### 9.1 三层音频能力

1. Preview Audio  
   用于游客模式或未绑定外部播放权限时的基础试听。

2. Local / Hosted Audio  
   用于后续可控的站内播放能力。MVP 至少支持用户导入非 DRM 的 `m4a` 文件并在站内播放器中播放。

3. Remote Provider Playback  
   用于 Spotify 等外部平台授权后的增强播放能力。

### 9.2 系统约束

- 不登录 Spotify，不能假设可以播放 Spotify 完整歌曲。
- `preview_url` 只能作为过渡型音频能力。
- 从本地导入的 `m4a` 文件要作为站内播放器的一等音源处理。
- 播放器要能感知“当前内容是否可播放、能否完整播放、来自哪个 Provider”。

## 10. Agent 设计

### 10.1 Agent 不是模型，而是执行系统

完整 Agent 至少包含：

1. 意图识别  
   判断是查询、推荐、控制播放、解释歌曲，还是多步任务。

2. 上下文读取  
   读取会话上下文、站内偏好、历史推荐、播放状态、Provider 能力。

3. 工具选择  
   选择目录查询、推荐、歌单写入、收藏写入、播放队列动作等工具。

4. 结果组织  
   返回回复文本、推荐结果、播放器动作、解释信息。

5. 记忆写回  
   将用户偏好、推荐结果、反馈信息写回站内长期记忆。

### 10.2 建议的 Agent 响应协议

```json
{
  "reply": "我根据你最近收藏和这周常听的氛围，整理了一组适合夜间学习的歌。",
  "intent": "recommend_music",
  "confidence": 0.91,
  "actions": [
    {
      "type": "player.replace_queue",
      "payload": {}
    }
  ],
  "artifacts": [
    {
      "type": "recommendation_set",
      "items": []
    }
  ],
  "toolCalls": [],
  "memoryWriteback": {
    "updated": true
  }
}
```

### 10.3 Agent 工具分类

- Catalog Tools  
  搜索、查歌曲、查艺人、查专辑、查歌单。

- Library Tools  
  建歌单、加歌、删歌、收藏、取消收藏。

- Recommendation Tools  
  生成推荐、改写推荐约束、切换历史版本。

- Player Tools  
  替换队列、追加队列、播放、暂停、上一首、下一首。

- Memory Tools  
  读取长期偏好、读近期行为、写回反馈标签。

- Provider Tools  
  导入 Spotify 歌单、同步外部收藏、读取外部用户画像。

## 11. 关键流程

### 11.1 游客搜索流

1. 用户打开页面，不登录。
2. 前端调用公开目录接口。
3. 后端通过 Provider 公开能力获取结果。
4. 前端展示公开元数据与可用预览。

### 11.2 站内歌单流

1. 用户登录 AgentMusic。
2. 创建站内歌单。
3. 搜索并添加歌曲引用。
4. 歌单和歌曲关联保存到站内数据库。

### 11.3 本地音频导入流

1. 用户登录 AgentMusic。
2. 选择本地音频文件。
3. 后端校验文件格式、文件大小和可播放性。
4. Local Media Service 提取元数据并写入 `audio_assets`。
5. 文件被纳入站内曲库，可加入歌单、收藏和播放队列。

### 11.4 Spotify 绑定流

1. 用户已登录站内账号。
2. 用户发起“连接 Spotify”。
3. 后端完成 Spotify OAuth。
4. 绑定关系写入 `provider_links`。
5. 用户可执行导入歌单、同步收藏、增强推荐。

### 11.5 Agent 推荐流

1. 用户发起自然语言请求。
2. Agent 读取站内会话、收藏、历史反馈。
3. 若用户绑定了 Spotify，则追加外部画像。
4. Recommendation Service 生成候选集。
5. Agent 返回回复、推荐卡片与播放器动作。
6. 结果写入推荐历史和长期记忆。

## 12. 安全与合规

- `client_secret` 只能保存在后端。
- 所有站内用户数据必须和外部 Provider token 分离存储。
- 对外部 Provider 数据设置最小权限原则。
- 不存储不应长期保存的受限音频内容。
- 对“游客模式 / 站内模式 / Provider 增强模式”做明确的权限边界。

## 13. 技术选型建议

- 前端：React + Vite + Redux Toolkit
- 后端：Node.js + Express
- 站内数据：SQLite 起步，后续可迁移 MySQL / PostgreSQL
- 缓存：内存缓存起步，后续 Redis
- Agent Runtime：Node.js 内的编排层
- 外部 Provider：Spotify 作为第一个适配器

不建议当前阶段做过重的微服务拆分。先把站内核心能力建好，再按 Provider 与 Agent 的边界逐步抽离。

## 14. MVP 边界

第一版完整可用产品，只需要做到：

1. 支持游客浏览公开目录
2. 支持站内账号注册 / 登录
3. 支持站内歌单和站内收藏
4. 支持本地 `m4a` 音频导入与站内播放
5. 支持 Agent 推荐 / 查询 / 播放队列控制
6. 支持推荐历史与会话记忆
7. 支持 Spotify 作为可选增强接入

达到这 7 点，项目就已经不是“Spotify Demo”，而是一个有独立产品骨架的 AI 音乐 Agent。
