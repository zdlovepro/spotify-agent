# AgentMusic 系统设计

## 1. 设计目标

AgentMusic 的目标不是再做一个普通播放器，而是做一个“能够理解用户意图、能调用音乐能力、能记住上下文、能产出历史推荐结果”的音乐 Agent。

系统设计需要同时满足 4 个目标：

1. 能稳定接入 Spotify，完成真实数据获取与基础播放闭环。
2. 能把自然语言请求转成结构化音乐操作，而不是只做文本聊天。
3. 能保留用户的长期偏好、会话上下文和历史推荐版本。
4. 能在后续继续扩展语音、歌词、队列管理、歌单编辑等能力，而不推翻现有代码。

## 2. 当前实现状态

### 已完成

- 前端：React + Vite + Redux Toolkit 的播放器界面已经具备基础框架。
- 后端：Node.js + Express 已接入 Spotify OAuth。
- 后端：已具备 Spotify 数据代理、搜索、推荐、聚合接口、推荐历史接口。
- 前端：已能在登录后读取真实 Spotify 歌单，并在有 `preview_url` 时播放歌曲预览。

### 还缺少

- 真正的 Agent 编排层。
- 聊天会话、消息历史、长期记忆。
- Tool calling / function calling 层。
- 用户自然语言到播放器动作的执行链。
- 语音输入输出。
- 推荐结果解释、推荐版本切换、推荐结果反馈闭环。

## 3. 总体架构

推荐采用“单仓前后端 + 后端 Agent 编排”的架构，保持当前 Node.js 技术栈连续性。

### 架构分层

1. Presentation Layer
   前端 React 应用，负责 UI、播放控制、聊天界面、语音输入、结果呈现。

2. Application API Layer
   Express 路由层，负责鉴权、会话管理、Agent 接口、业务编排入口。

3. Domain Service Layer
   负责 Spotify 领域能力、推荐历史、用户画像、聊天会话、Agent tool 封装。

4. Agent Orchestration Layer
   负责意图识别、计划生成、工具调用、结果汇总、记忆读写。

5. Infrastructure Layer
   Spotify API、LLM API、缓存、数据库、对象存储、日志监控。

## 4. 推荐的核心模块

### 4.1 前端模块

- Auth Module
  处理 Spotify 登录、token 管理、用户身份展示。

- Player Module
  处理当前播放队列、进度条、上下首、播放模式、音量。

- Chat Module
  处理中间聊天窗口、会话历史、消息流式输出、Agent 状态。

- Recommendation History Module
  展示 Agent 历史推荐歌单，支持切换、删除、再次播放。

- Context Panel Module
  展示当前歌曲、艺人信息、歌词、推荐解释。

- Voice Module
  处理 Web Speech API 或浏览器录音上传。

### 4.2 后端模块

- Auth Service
  管理 Spotify OAuth、refresh token、用户身份确认。

- Spotify Service
  已有基础能力，继续扩展播放队列、歌单编辑、艺人详情、歌词桥接。

- Agent Service
  新增的核心模块，负责接收自然语言请求，驱动工具调用。

- Conversation Service
  保存用户会话、消息、Agent 执行轨迹。

- Memory Service
  保存长期偏好、近期行为、用户反馈、推荐偏好标签。

- Recommendation Service
  封装推荐生成、推荐版本管理、推荐解释、推荐反馈学习。

- Playback Command Service
  将 Agent 产出的动作映射成统一播放指令。

- Observability Service
  记录 prompt、tool 调用、错误、耗时、命中率。

## 5. Agent 核心设计

### 5.1 Agent 不是单个模型，而是一个执行系统

完整 Agent 至少包含 5 个环节：

1. 输入理解
   把用户请求解析成意图、约束、上下文变量。

2. 计划生成
   判断是查数据、做推荐、控制播放、解释歌曲，还是多步组合任务。

3. 工具执行
   调 Spotify、读历史推荐、读用户画像、查当前播放状态。

4. 回答生成
   产出自然语言回复 + 结构化 UI 结果 + 可执行动作。

5. 记忆更新
   把用户偏好、反馈、推荐结果写回长期记忆与历史记录。

### 5.2 建议的 Agent 输入输出协议

前端向后端发送：

```json
{
  "conversationId": "uuid",
  "message": "给我来点适合晚上学习的电子乐，不要太吵",
  "context": {
    "currentTrackId": "xxx",
    "currentPlaylistId": "yyy",
    "locale": "zh-CN"
  }
}
```

后端 Agent 返回：

```json
{
  "reply": "我给你整理了一组更适合夜间专注的电子乐。",
  "intent": "generate_recommendation",
  "actions": [
    {
      "type": "replace_queue",
      "payload": {
        "tracks": []
      }
    }
  ],
  "artifacts": {
    "recommendationId": "uuid",
    "tracks": [],
    "reasoningSummary": "基于低能量、器乐优先、电子氛围"
  }
}
```

### 5.3 Agent Tool 定义

建议先做以下工具：

- `spotify.search`
- `spotify.get_playlist`
- `spotify.get_artist`
- `spotify.get_track`
- `spotify.get_recommendations`
- `spotify.get_user_top_tracks`
- `spotify.get_user_top_artists`
- `library.get_saved_tracks`
- `history.list_recommendations`
- `history.save_recommendation`
- `memory.read_user_profile`
- `memory.update_user_profile`
- `player.get_state`
- `player.replace_queue`
- `player.enqueue_tracks`
- `player.play_track`

### 5.4 意图分类

建议首期支持 6 类意图：

1. `play_music`
2. `generate_recommendation`
3. `search_entity`
4. `explain_music`
5. `manage_playlist`
6. `control_player`

### 5.5 推荐生成逻辑

推荐不应该完全依赖 LLM 直接编歌单，而应该采用“LLM 负责理解，推荐服务负责执行”。

建议流程：

1. 用户输入自然语言需求。
2. LLM 提取推荐约束：
   情绪、风格、语言、年代、能量、是否人声、是否熟悉、是否随机。
3. Recommendation Service 结合：
   用户长期偏好、近期播放、收藏歌曲、Top Tracks、历史推荐反馈。
4. 生成 seed artists / seed tracks / seed genres。
5. 调 Spotify recommendations + search 做候选集。
6. 后端排序、去重、过滤无预览曲目。
7. 生成推荐解释并写入历史版本。

## 6. 数据设计

当前后端已有本地 JSON 推荐历史；要完成 Agent，建议逐步迁移到数据库。

### 6.1 推荐的核心表

- `users`
  存 Spotify 用户基础信息、本地系统用户标识。

- `spotify_tokens`
  存 refresh token、过期时间、scope。

- `conversations`
  会话主表。

- `messages`
  用户消息、Agent 回复、工具执行摘要。

- `recommendation_sets`
  一次推荐结果的元信息。

- `recommendation_tracks`
  某个推荐集内的歌曲列表与排序。

- `user_memory_profile`
  长期偏好画像，如风格、艺人、语言、场景偏好。

- `feedback_events`
  喜欢、跳过、删除、保存、重复播放等反馈。

### 6.2 第一阶段可接受的落地方案

- 会话：先本地 SQLite。
- 推荐历史：继续 JSON 或切 SQLite。
- 缓存：先内存缓存，后续切 Redis。

## 7. 关键业务流

### 7.1 登录流

1. 前端点击登录。
2. 后端跳转 Spotify OAuth。
3. Spotify 回调后端。
4. 后端换 token。
5. 跳回前端，前端保存 session。

### 7.2 推荐流

1. 用户输入“给我来点晚上学习的电子乐”。
2. 前端调用 `/api/agent/chat`。
3. Agent 读取：
   当前上下文 + 用户画像 + 历史推荐。
4. Agent 选择工具并生成 seed。
5. Recommendation Service 调 Spotify。
6. 结果写入 `recommendation_sets`。
7. 返回聊天结果 + 推荐歌曲 + 播放动作。

### 7.3 播放控制流

1. 用户输入“切到随机模式，给我下一首”。
2. Agent 识别为 `control_player`。
3. 读取当前 player state。
4. 输出结构化动作。
5. 前端播放器执行。
6. 执行结果回传后端写入行为日志。

## 8. 非功能设计

### 性能

- Spotify 聚合接口优先后端缓存。
- 歌单详情懒加载。
- Agent 回复支持流式返回。
- 推荐结果分页与分层加载。

### 安全

- refresh token 只放后端。
- 前端避免长期存 access token。
- 所有 Agent 接口都要求会话校验。
- 对 prompt、工具参数、用户输入做日志脱敏。

### 可观测性

- 记录每次意图识别结果。
- 记录工具调用次数、失败率、耗时。
- 记录推荐命中率与用户反馈。

## 9. 技术路线建议

结合当前代码，建议继续采用：

- Frontend: React + Redux Toolkit + React Router
- Backend: Node.js + Express
- Agent Runtime: Node.js 内的 Agent Orchestrator
- LLM 接入：独立 `llm-service`
- DB: SQLite 起步，后续 MySQL / PostgreSQL
- Cache: 内存缓存起步，后续 Redis

不建议现在立刻引入过重的多语言微服务拆分。先把 Agent 跑通，再做分层拆分。

## 10. MVP Agent 边界

第一版完整 Agent 只需要做到：

1. 文本输入聊天。
2. 能识别推荐 / 播放 / 查询三类核心意图。
3. 能用 Spotify 数据生成推荐结果。
4. 能把推荐结果写入历史版本。
5. 能返回结构化播放器动作。
6. 能基于用户最近偏好做最基础个性化。

达到这 6 点，就已经是“可用 Agent”，不是单纯 demo。
