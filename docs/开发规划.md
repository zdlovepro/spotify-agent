# AgentMusic 开发规划

## 1. 开发目标

目标是在当前已打通 Spotify OAuth 和基础真实数据能力的基础上，完成一个可用的音乐 Agent MVP，并逐步演进到可持续扩展的产品。

## 2. 当前阶段判断

### 已有基础

- Spotify 登录链路已通。
- 前后端已具备真实 Spotify 数据接入。
- 后端已有推荐历史、搜索、推荐、聚合接口。
- 前端已有播放器框架、歌单页、基础播放闭环。

### 当前最大缺口

- 没有真正的聊天式 Agent 接口。
- 没有用户记忆和会话层。
- 没有推荐解释和推荐反馈闭环。
- 播放动作和聊天结果还未统一。

## 3. 开发原则

1. 先闭环，再扩展。
2. 先文本 Agent，再语音 Agent。
3. 先做可控的工具式 Agent，再追求复杂 Planner。
4. 先做结构化动作输出，再做复杂 UI 花活。
5. 先保证推荐质量与稳定性，再做高阶功能。

## 4. 分阶段规划

## 阶段 A：稳固 Spotify 基础层

### 目标

把当前 Spotify 接入从“能用”提升到“够稳定支撑 Agent”。

### 任务

- 完善前端对 `/api/spotify/home`、`/api/spotify/library/overview` 的使用。
- 统一前端数据模型，减少 mock 和真实数据双轨逻辑。
- 完成艺人页、专辑页、搜索真实检索页。
- 补充播放队列、随机模式、循环模式、队列查看接口设计。
- 给推荐历史加前端展示和切换能力。

### 产出

- 一个完整的“真实 Spotify 数据驱动”的播放器壳子。

## 阶段 B：做出 Agent MVP

### 目标

做出第一版可用的文本音乐 Agent。

### 必做接口

- `POST /api/agent/chat`
- `GET /api/agent/conversations/:id`
- `POST /api/agent/conversations`
- `POST /api/agent/feedback`

### 必做模块

- Conversation Service
- Intent Classifier
- Tool Registry
- Recommendation Service v1
- Memory Profile v1

### 必做能力

- 用户说“给我推荐 xxx”
- 用户说“播放 xxx”
- 用户说“介绍一下当前这首歌/这个歌手”
- Agent 能返回：
  - 文本回复
  - 推荐结果
  - 播放动作
  - 推荐历史记录

### MVP 完成标准

- 至少支持 3 类意图：
  - 推荐
  - 播放
  - 查询
- Agent 指令成功率达到 70% 以上
- 一次请求平均响应时间控制在 3 秒内

## 阶段 C：做出记忆与推荐迭代

### 目标

让 Agent 从“一次性工具”升级成“记得住你的音乐助手”。

### 任务

- 增加用户长期偏好画像。
- 引入反馈事件：
  喜欢、跳过、收藏、重新生成、删除推荐。
- 让推荐生成时纳入：
  - Top Tracks
  - Top Artists
  - Saved Tracks
  - Recent Recommendation History
  - Feedback Events
- 为推荐结果生成解释：
  为什么推荐、和用户偏好有什么关系。

### 完成标准

- 推荐结果可解释。
- 历史推荐可切换、可复播、可删除。
- 推荐反馈能影响后续结果。

## 阶段 D：做语音 Agent

### 目标

加入浏览器端语音输入，让 Agent 从聊天工具变成真正的操作入口。

### 任务

- Web Speech API 或录音上传接口。
- 语音转文本。
- 文本进入统一 Agent 链路。
- 可选文本转语音回复。

### 注意

- 语音不是单独系统，要复用文本 Agent。
- 不要做第二套 Agent 逻辑。

## 阶段 E：做产品化与工程化

### 目标

为后续 demo、答辩或持续迭代做好准备。

### 任务

- 数据库存储替换本地 JSON。
- 接入 Redis。
- 增加日志、追踪、错误报警。
- 增加基础测试。
- 增加 prompt versioning。
- 增加 feature flag。

## 5. 推荐开发顺序

建议严格按下面顺序推进：

1. 去掉前端主要页面里的 mock 依赖。
2. 接入推荐历史前端展示。
3. 设计并实现 `/api/agent/chat`。
4. 做前端聊天面板。
5. 做推荐动作和播放器动作统一协议。
6. 加会话历史。
7. 加用户画像与反馈。
8. 加语音。

## 6. 接下来 3 个迭代的具体安排

## 迭代 1

### 目标

把“播放器壳子”做完整。

### 任务

- 首页改用 `/api/spotify/home`
- Library 页改用 `/api/spotify/library/overview`
- 搜索页接真实 `/api/spotify/search`
- 历史推荐页接 `/api/history/recommendations`
- 新增 Artist 页面

### 完成标志

- 页面主要内容不再依赖本地 mock

## 迭代 2

### 目标

做 Agent API 和聊天 UI。

### 任务

- 后端实现 `/api/agent/chat`
- 接入 LLM
- 先支持推荐、播放、查询三类意图
- 前端新增聊天主面板
- 返回推荐列表和动作指令

### 完成标志

- 用户输入一句话，系统能返回可执行推荐结果

## 迭代 3

### 目标

让 Agent 具备“记忆”和“版本管理”。

### 任务

- Conversation 持久化
- Message 持久化
- User Memory Profile
- Feedback API
- 历史推荐切换与解释

### 完成标志

- Agent 能体现基础个性化

## 7. 风险与应对

### 风险 1：Spotify 预览音频有限

应对：

- MVP 阶段默认以 `preview_url` 作为试听验证方式。
- 对无预览音频曲目明确标记不可播。

### 风险 2：Agent 太早做复杂 Planner

应对：

- 第一版只做固定意图分类 + 工具调用。
- 暂不做开放式自主多步规划。

### 风险 3：记忆做太早导致复杂度失控

应对：

- 先做显式用户画像与推荐历史。
- 后做自动提炼式长期记忆。

### 风险 4：前后端协议不稳定

应对：

- 尽快定义统一的 `reply + actions + artifacts` 响应结构。

## 9. Definition of Done

项目达到“完整 Agent”的标准应是：

1. 用户可登录并访问真实 Spotify 数据。
2. 用户可用自然语言提出音乐需求。
3. Agent 能识别意图并调用工具。
4. Agent 能给出推荐或执行播放动作。
5. 系统能保存会话与历史推荐版本。
6. 推荐结果能体现基础个性化。
7. 前端可以完整展示和操作这些结果。
